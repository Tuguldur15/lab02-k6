## 2. SLO ба Threshold Тохируулсан Үндэслэл
- **Baseline хэмжилт:** 5 VU ачаалалтай үеийн p95 latency **326.93 ms** гарсан.
- **SLO Босго тогтоосон шалтгаан:** Хэрэглэгчийн хүлээлгийн хугацааг хянах ба SLO босго тогтоох зорилгоор `http_req_duration` дээр `p(95) < 375ms`, харин найдвартай ажиллагааг хангахын тулд `http_req_failed` дээр `rate < 0.01` (`< 1%`) threshold тохируулсан.
- **Шалгалтын үр дүн:** `script.js` дээрх 5 VU ба 100 VU туршилтуудад `p(95)` болон алдааны хувь тогтоосон босгыг давж **PASS** гарсан. Харин `script-fail.js` дээр босгыг санаатайгаар `p(95) < 50ms` болгож хатууруулахад бодит `p(95) = 244.1 ms` гарч threshold зөрчигдөн **FAIL** болж Quality Gate зарчим батлагдсан.

## 3. Дүгнэлт ба Ажиглалт (8-10 өгүүлбэр)
1. Grafana k6 хэрэгслээр зэрэгцээ виртуал хэрэглэгчийн тоог (VU) 5 ба 100 (мөн 30 VU) түвшинд шатлан өсгөж, `https://test.k6.io` веб байгийн хариу олгох хугацаа (latency) болон нэвтрүүлэх чадварыг (throughput) туршин хэмжлээ.
2. 5 VU baseline хэмжилтээр `p(90) = 288.49 ms`, `p(95) = 326.93 ms` байсан бөгөөд нэгж секундэд дунджаар `7.25 req/s` (`450` хүсэлт) гүйцэтгэж, алдааны хувь `0.00%` гарсан.
3. Ачааллыг 100 VU болгож өсгөхөд throughput `149.89 req/s` (`9,186` хүсэлт) хүртэл өссөн ч `p(95)` хугацаа `258.04 ms` хэвээр байж, алдааны хувь мөн `0.00%` гарсан нь туршилтын орчин тухайн ачааллыг тогтвортой дааж байгааг харууллаа.
4. Гэсэн хэдий ч ачаалал өсөх тусам хамгийн удаан хариуны (`max`) хэмжээ 5 VU үед `992.77 ms` байснаас 100 VU үед `1.61s` болж нэмэгдсэн нь оргил ачааллын үеийн урт сүүлийн (tail latency) өөрчлөлтийг анхаарах ёстойг илтгэнэ.
5. SLO threshold-ийг кодоор тодорхойлсноор гүйцэтгэлийн хэмжүүрийг автоматаар үнэлэх боломжтой болсон.
6. `script-fail.js` туршилтаар `p(95) < 50ms` босго тавихад `p(95) = 244.1 ms` гарч `thresholds on metrics 'http_req_duration' have been crossed` алдаа буюу **FAIL** төлөв үүссэн.
7. Энэ нь автоматжуулсан pipeline эсвэл чанарын хяналтын шатанд SLO зөрчигдсөн тохиолдолд түгээлтийг зогсоох Quality Gate хэрхэн ажилладгийг практикт баталлаа.
8. Мөн бодит хэмжилтийн тайлан болон гаралтын файлуудыг (`results/run-*.txt`) GitHub репозиторид хадгалснаар туршилтын үр дүнг дахин нягтлах, баталгаажуулах нөхцөл бүрдсэн.
